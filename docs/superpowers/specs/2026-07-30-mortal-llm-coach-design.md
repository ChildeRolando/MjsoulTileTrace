# 双引擎 LLM 日麻教练设计规格

日期：2026-07-30
状态：已确认

补充约束：决策解释、攻守后处理、牌河阅读、证据来源和严格模式必须遵守
[`2026-07-30-evidence-grounded-coach-reasoning-design.md`](./2026-07-30-evidence-grounded-coach-reasoning-design.md)。
麻将模型不提供可验证的内部原因，教练不得声称知道模型为何选择某个动作。

## 1. 产品目标

开发一个仅在用户电脑上运行的类 Agent 工具。用户完成一次性 LLM 设置后，每次只需提交一个雀魂牌谱 URL，工具便会：

1. 匿名获取 URL 对应的完整牌谱；
2. 从 URL 识别主视角；
3. 使用用户为该会话选择的官方 Mortal 4.1b 或本地 Akagi Native，分析整盘所有主视角决策；
4. 把所选模型输出转换为统一、稳定、可验证的结构化数据；
5. 依据可调阈值，把错误分为详细讲解和一句话简评；
6. 由 LLM 教练主动发起会话，给出逐错分析和整盘总结；
7. 允许用户在牌局任意时点继续追问；
8. 像 Agent 会话一样保存和恢复历史牌谱及对话。

产品的核心不是重新实现麻将 AI，而是把麻将模型的决策证据、可操作的牌局回放和有上下文的 LLM 教学组织成一个可靠的本地 Agent。Mortal 4.1b 与 Akagi Native 是两个并列的正式模型选项；LLM 教练必须以当前会话所选模型的结果为正式分析依据，不得把 Akagi 降格为预览或非正式结果。

## 2. 首版范围

### 2.1 支持

- 雀魂分享牌谱 URL；
- 常规四人麻将南风局；
- URL 指定的主视角；
- 弃牌、吃、碰、杠、立直、默听、和牌等主视角可选决策；
- 官方 Mortal 4.1b 人工验证接力分析；
- 应用管理的本地 Akagi Native 分析；
- 新建会话时选择模型，并为该会话冻结模型；
- OpenAI 兼容 LLM 接口；
- 一牌谱一会话；
- 本机会话历史、重命名、删除和恢复；
- 牌局回放、错误跳转、逐切跳转和完整事件步进；
- 每条聊天消息绑定发送瞬间的牌局局面。

### 2.2 不支持

- 三人麻将；
- 东风局；
- 特殊规则牌局；
- 天凤、雀姬、雀城等其他平台；
- 公网部署、多用户、云同步和移动端原生应用；
- 绕过或自动完成公开 Mortal 网站的 Cloudflare Turnstile；
- 把非官方 Mortal 测试权重冒充官方 Mortal 4.1b；
- 使用来源、授权或强度无法验证的社区 Mortal 权重；
- 首版接入 akochan、MJAPI 或 Akagi 付费云模型；
- 雀魂登录、Cookie、账号授权或任何凭据备用流程；
- 用 LLM 替代、覆盖或伪造当前所选麻将模型的原始判断。

不支持的牌谱应在分析前被拒绝，并给出具体原因，不生成可能误导的部分报告。

## 3. 关键外部约束

- `https://mjai.ekyu.moe` 的公开提交流程受 Cloudflare Turnstile 保护，不能作为后台自动化接口。
- 官方 Mortal 训练权重不公开，因此首版不得声称本地集成官方 Mortal 4.1b。
- Mortal 模式采用明确的人机接力：应用打开官方页面并辅助复制牌谱 URL；用户亲自完成 Turnstile 和提交；应用接收结果 URL 后匿名下载、解析结果。应用不得破解、代答或绕过验证。
- Akagi Native 模式完全在本机执行。应用固定并管理经过校验的 Akagi 版本和原生权重，不要求普通用户配置可执行文件或模型路径。
- 雀魂牌谱获取严格为匿名流程。实现不得引入登录、Cookie 或账户状态。
- Mortal 与 Akagi 的候选分数都不是胜率、打点损失或期望值。产品统一使用“模型选择分”和“模型选择分差”，同时保留引擎原始 logits、Q 值或概率供审计。
- 两种模型的强度证据不同。界面必须显示当前模型名称；Mortal 可标注“官方 4.1b”，Akagi 可标注“本地 Native”，但不得用“正式/非正式”“裁判/预览”等措辞制造报告等级差异。

## 4. 用户流程

### 4.1 首次设置

用户只需设置：

- OpenAI 兼容 Base URL；
- API Key；
- 模型名；

应用自动检查受管 Akagi Native 运行时。若尚未安装，则准备固定版本的程序和内置权重，校验完整性后完成运行测试。首版不暴露 Akagi 可执行文件或模型路径设置。

Mortal 模式没有本地运行时设置。首次选用时，应用解释一次人工验证接力流程并记录用户已知悉，不保存 Mortal 或雀魂账户状态。

LLM 连接测试通过后即可进入工作台；Akagi 运行测试失败只影响选择 Akagi 的新会话，不妨碍用户使用 Mortal 人工接力。

API Key 保存到 Windows 凭据管理器。前端只接收“已配置”状态，不得读取完整密钥。Base URL、模型名、阈值等非敏感设置保存在本机应用配置中。

### 4.2 新建分析

1. 用户点击“新分析”；
2. 粘贴雀魂 URL；
3. 应用解析回放标识和主视角；
4. 应用校验四麻、南风局和常规规则；
5. 用户选择“官方 Mortal 4.1b”或“本地 Akagi Native”，默认使用上一次选择；
6. 创建一个新会话并冻结模型选项；
7. Akagi 模式在后台依次执行牌谱获取、格式转换、本地推理、结构化和教练生成；
8. Mortal 模式进入人工验证接力：打开官方页面、复制牌谱 URL、等待用户完成验证和提交，再由用户粘贴 Mortal 结果 URL；
9. 应用校验结果 URL、匿名下载并解析结果，核对牌谱标识和主视角后生成教练报告；
10. 前端实时显示阶段、需要用户操作的节点和进度；
11. 教练生成完成后主动发送开场报告。

Mortal 结果 URL 是每次分析的一次性输入，不是登录凭据。应用不得接受任意站点 URL，只允许受信任的 Mortal 结果来源，并对下载大小、重定向和内容类型设限。

### 4.3 继续追问

用户在中央牌桌导航到任意局面并发送消息。发送时应用冻结当前牌局快照，并作为隐藏上下文附加到该条消息。用户随后导航到其他位置，不会改变历史消息绑定的局面。

### 4.4 历史会话

每份牌谱分析是独立会话。历史列表显示自动生成的牌局名称、日期、最终名次、重点错误数和状态。用户可重新打开、继续追问、重命名或删除会话。

## 5. 界面设计

### 5.1 总体布局

桌面宽屏采用三栏结构：

- 左栏：会话历史和“新分析”；
- 中栏：视觉中心，展示牌桌、回放和决策热力；
- 右栏：教练开场报告、当前错误讲解和后续对话。

窄屏下，会话栏和对话栏变为可打开的抽屉，牌局区域保持主视图。

### 5.2 中央牌局区

中央牌局区展示：

- 四家牌河；
- 四家鸣牌和立直状态；
- 我方手牌与当前摸牌；
- 宝牌指示牌；
- 场风、自风、局数、本场、立直棒、剩余牌数；
- 四家点数和当前顺位；
- 当前事件与主视角可选动作。

在主视角可操作时，每个候选动作直接显示当前模型的选择分和热力。模型首选与实战动作必须有不同且不只依赖颜色的标记。模型名称在牌桌区持续可见。

### 5.3 控制器语义

- 上一局 / 下一局：移动到相邻局的开始位置；
- 上一错误 / 下一错误：移动到相邻的主视角非首选决策；
- 上一切牌 / 下一切牌：移动到相邻的主视角弃牌决策；
- 后退 / 前进：沿完整牌局事件流移动一个原子事件，包括摸牌、弃牌、鸣牌、立直和结算。

导航不会自动发送消息，也不会改变历史消息已绑定的快照。

### 5.4 右侧教练区

右侧显示：

- 教练主动开场报告；
- 当前错误的详细或简略讲解；
- 当前模型的原始候选证据；
- 用户追问与教练回复；
- 消息输入框；
- 当前消息将附加哪个牌局位置的轻量提示。

## 6. 系统架构

首版采用本地 Web Agent：

- React + TypeScript 前端；
- Node.js + TypeScript 本机服务；
- SQLite 本地数据库；
- 可替换的麻将分析引擎接口；
- Akagi Native 本地适配器；
- Mortal 结果 HTML 下载与解析适配器；
- OpenAI 兼容 LLM 客户端；
- SSE 进度和消息流。

建议代码边界：

- `coach/web`：工作台、牌局回放、热力牌面和聊天；
- `coach/server`：本机 API、任务编排、安全存储和进程管理；
- `coach/contracts`：跨前端、服务端、数据库和 LLM 的共享运行时数据契约。
- `coach/engines/akagi-native`：固定版本 Akagi 运行时、回放适配和候选输出；
- `coach/engines/mortal-review`：受信任结果 URL 校验、HTML 解析和统一数据转换。

现有静态教学站点继续独立工作。教练项目可复用现有 `assets/tiles` 素材，但不得破坏原页面和测试。

## 7. 数据流

```text
雀魂 URL
  → URL 解析与主视角识别
  → 匿名牌谱获取
  → 统一牌谱格式转换
  → [本地 Akagi Native | Mortal 人工验证结果]
  → 所选模型输出解析与结构化
  → 五轴证据编译与双向候选因素账本
  → 模型选择分差计算与阈值分流
  → LLM 教练生成
  → SQLite 会话与消息
  → 牌局工作台
```

各阶段通过稳定的数据契约连接。牌谱获取、模型适配、结构化和 LLM 均为可单独测试和替换的模块。两个引擎必须输出同一个 `NormalizedAnalysis` 契约，LLM 层不得依赖某个引擎私有字段。

## 8. 结构化分析模型

### 8.1 会话

会话至少记录：

- 会话 ID；
- 原始 URL；
- 回放 ID；
- 主视角标识和座位；
- 牌局元数据；
- 任务状态和失败阶段；
- 分析引擎：`mortal_review` 或 `akagi_native`；
- 模型显示名、引擎版本、模型/网络标识、配置摘要；
- 引擎原始分数类型及其归一化方法；
- LLM Base URL 标识和模型名，不含 API Key；
- Mortal 结果 URL 的安全摘要或 Akagi 受管运行时版本；
- 创建、更新和完成时间；
- 自动标题与用户标题。

### 8.2 牌局事件

事件流按确定顺序记录整盘动作。每个事件具有稳定事件 ID、局 ID、事件序号、操作者、动作类型和动作数据。

### 8.3 决策

每个主视角决策至少记录：

- 决策 ID、局和事件位置；
- 发送给所选模型或由其结果重建的完整可见状态；
- 手牌、摸牌、牌河、鸣牌、宝牌、点数、巡目和剩余牌数；
- 合法候选动作；
- 实战动作；
- 模型候选排序、原始分数和归一化选择分；
- 模型首选；
- 模型选择分差；
- 模型动作与实战动作的五轴候选账本；
- 支持模型动作、支持实战动作、无差异和未知因素；
- 每项因素的来源、置信等级、证据 ID 和限制；
- 教练规则 ID、版本和教练自己的建议；
- 固定为未知的模型内部原因；
- 是否为错误；
- 是否超过详解阈值；
- 讲解状态和结构化讲解。

动作标识必须能区分赤牌、普通五、立直弃牌、普通弃牌及不同鸣牌组合，不能只按牌面文本合并。

### 8.4 消息与牌局快照

每条用户消息持久化：

- 消息文本；
- 发送时间；
- 当时会话 ID；
- 局 ID；
- 事件 ID；
- 可选决策 ID；
- 完整 `scene_snapshot`；
- 对应教练回复。

`scene_snapshot` 是不可变快照，不是指向“当前播放器状态”的动态引用。

## 9. 模型选择分差和阈值

两个适配器都必须为每个合法候选输出 0–100 的归一化模型选择分。Mortal 适配器使用结果页提供的候选概率；Akagi 适配器使用对合法动作 logits 计算的 softmax 概率。原始值必须原样保存，不允许只保存归一化结果。

```text
模型选择分 = 候选动作概率 × 100
模型选择分差 = 模型首选选择分 - 实战动作选择分
```

如果结果页或本地适配器无法为全部合法动作提供可比较概率，该决策标记为“模型证据不完整”，不得参与阈值错误排名，但仍可显示原始数据。模型选择分不描述胜率、打点或 EV，不同引擎之间的选择分也不可直接比较。

- 默认详解阈值：10；
- 用户可在设置中调整；
- 实战动作是当前模型首选时，不计为错误；
- 所有非首选决策均保留；
- 高于或等于阈值的错误生成完整讲解；
- 低于阈值的错误生成一句具体简评。

一次会话必须冻结分析时使用的阈值。用户改变全局阈值只影响新会话；重新分级旧会话必须是显式操作，避免历史报告悄然变化。

## 10. 教练输出契约

### 10.1 教练开场

分析完成后，教练主动发送开场报告，包含：

1. 整盘表现；
2. 最重要的改进主题；
3. 高阈值错误数和低阈值偏差数；
4. 按重要性排序的错误目录；
5. 每局简评；
6. 整盘总结和下一步训练建议。

每个高阈值错误的详细讲解预先生成并绑定到决策。用户通过错误导航查看，不要求把所有长文堆叠在一条聊天消息中。

### 10.2 高阈值错误

完整讲解必须包含：

- 实战动作；
- 推荐动作；
- 关键候选比较；
- 错误的具体原因；
- 引用的局面证据；
- 牌效、打点、速度、防守或顺位层面的影响；
- 可迁移到其他牌局的判断原则；
- 对解释置信度的诚实说明。

### 10.3 低阈值错误

一句话简评也必须包含：

- 推荐动作或候选比较；
- 至少一个具体原因；
- 至少一个对应的可见证据。

允许的证据包括现物数量、牌形连接、有效进张、巡目、点差、宝牌、安全度、鸣牌和牌河信息。

禁止只有以下内容的空泛简评：

- “实战选择可以理解”；
- “两者差距不大”；
- “Mortal 更喜欢某牌”；
- “这是一个小错误”；
- 任何没有引用局面事实的泛泛判断。

若结构化证据不足以可靠解释微弱偏好，必须明确写出“当前结构化证据不足以可靠解释这项微弱偏好”，不得编造因果理由。

### 10.4 事实与解释

所选模型的动作和选择分属于结构化事实。LLM 的麻将理由属于解释。界面和数据结构必须保留两者边界，避免用户把 LLM 推测误认为模型原始输出。

教练不得把任何解释描述为 Mortal 或 Akagi 的内部原因。核心解释由确定性因素账本和版本化教学规则生成；LLM 只负责受约束的教学表达。每个决策必须同时保留支持模型动作和支持实战动作的因素，禁止只挑选能事后合理化模型首选的证据。

## 11. 隐藏提示词协议

每次 LLM 请求由五层组成：

1. 固定教练角色、术语、证据要求和禁止事项；
2. 当前会话的整盘摘要和错误索引；
3. 当前用户消息冻结的完整牌局快照；
4. 当前决策的五轴候选账本、双向因素和教学规则；
5. 当前会话中必要的对话历史。

普通追问不重复发送整份原始牌谱，但必须始终发送用户发送消息时看到的完整有效局面。教练开场生成可以访问整盘结构化分析。

LLM 输出使用运行时模式校验。高阈值讲解和低阈值简评都必须提供可解析的证据引用。缺少必填字段、出现空泛话术、引用不存在的牌局事实、隐藏反方因素、改变计算数值或声称知道模型内部原因时，该项输出视为无效并单独重试。

## 12. 会话任务状态与恢复

会话状态机：

```text
created
→ fetching_replay
→ validating_replay
→ [preparing_akagi → running_akagi | awaiting_mortal_verification → importing_mortal_result]
→ normalizing
→ generating_coach
→ ready
```

任意阶段可进入 `failed`，同时记录：

- 失败阶段；
- 用户可读错误；
- 内部诊断码；
- 可安全记录的日志摘要；
- 可重试起点。

恢复规则：

- 从失败阶段重试；
- 已成功的中间产物不重复生成；
- 模型分析成功而 LLM 失败时，牌桌和结构化结果仍可查看；
- 单个错误讲解失败时，只重试该错误；
- 应用重启后恢复未完成会话；
- 不静默切换麻将模型、Mortal 网络或 LLM。

## 13. 本地存储与安全

- API Key 只保存在 Windows 凭据管理器；
- SQLite 不保存 API Key；
- 前端不接收 API Key；
- 日志必须过滤密钥、授权头、完整请求体和敏感路径；
- 雀魂侧不保存任何凭据；
- 数据库、日志和会话文件保存在用户本地应用数据目录；
- 默认 Akagi Native 程序、内置权重和版本清单位于应用管理的本机运行时目录；
- Mortal 结果导入只允许 HTTPS、受信任主机、有限重定向、有限响应大小和预期 HTML 内容；
- Mortal 结果 URL 不视为账号凭据，但日志只记录脱敏摘要，不记录完整查询参数；
- 删除会话时删除该会话的牌谱、中间结果、讲解和消息。

## 15. 验收标准

首版完成必须同时满足：

1. 用户只需完成一次性 LLM 设置；Akagi 不要求路径配置，Mortal 不要求账号登录；
2. 不需要雀魂登录或 Cookie；
3. 非四麻南风局被清楚拒绝；
4. 新建会话时可选择 Mortal 4.1b 或 Akagi Native，选择后不静默切换；
5. 两个模型的结构化结果和 LLM 报告具有相同产品地位；
6. Mortal 模式明确等待用户亲自完成 Turnstile，随后能安全导入结果；
7. Akagi 模式完全本地运行且不要求用户配置模型路径；
8. 能展示完整牌局、主视角手牌、四家牌河、宝牌和点数；
9. 控制器按本规格精确导航；
10. 当前模型选择分直接显示在候选牌或动作上；
11. 默认阈值为 10；
12. 所有非首选决策都有讲解；
13. 高阈值错误有完整分析；
14. 低阈值错误有具体原因和证据，不输出片汤话；
15. 教练主动发送整盘开场报告；
16. 每条用户消息都绑定发送瞬间的不可变牌局快照；
17. 分析失败可从正确阶段恢复；
18. 历史会话可保存、恢复、重命名和删除；
19. API Key 不进入前端、SQLite、仓库或日志；
20. 现有教学网站及其测试不受破坏。

## 16. 实施风险与控制

### 匿名牌谱获取发生协议变化

牌谱获取器保持独立边界并使用固定夹具测试。若匿名接口不可用，应用应明确报错；首版不以登录流程绕过。

### Mortal 结果页变化

解析层使用版本化选择器和脱敏 HTML 夹具。解析失败时保留原会话并明确要求更新适配器，不使用 LLM 猜测页面数据。

### Mortal 人工接力中断

`awaiting_mortal_verification` 是可持久化的正常状态而非失败。用户关闭应用后可继续；导入结果时必须核对牌谱标识、主视角和网络为 4.1b。

### Akagi Native 强度与版本

界面始终显示“Akagi Native”和固定版本，不冒充 Mortal。升级程序或权重必须更新版本清单、校验和和回归夹具；已有会话继续保留原版本信息。

### LLM 编造原因

不要求 LLM 猜测或验证麻将模型的隐藏原因。系统先生成五轴候选账本、双向因素和版本化教学判断，LLM 只表达这些证据。校验器拒绝不存在的证据、数值变更、单边挑选和模型因果归因；证据不足时必须明确表示无法可靠解释或不给出教学建议。

### 长牌谱导致提示词过大

开场生成使用整盘结构化摘要和分批错误讲解；普通追问只发送整盘摘要、错误索引、必要历史和当前冻结快照。

### 本机任务资源竞争

本地推理和教练生成任务通过队列限制并发。前端显示排队、人工等待和运行状态，应用退出或重启后恢复任务。

### Akagi 运行时准备或校验失败

应用使用固定版本、校验和与可恢复准备流程。失败时显示下载、校验或运行测试中的具体阶段并允许重试，不要求普通用户通过手工填写路径来绕过失败。用户仍可选择 Mortal 完成新的正式分析。
