# Mortal LLM 日麻教练设计规格

日期：2026-07-30
状态：待用户审阅

## 1. 产品目标

开发一个仅在用户电脑上运行的类 Agent 工具。用户完成一次性 LLM 设置后，每次只需提交一个雀魂牌谱 URL，工具便会：

1. 匿名获取 URL 对应的完整牌谱；
2. 从 URL 识别主视角；
3. 使用本机 Mortal 分析整盘所有主视角决策；
4. 把 Mortal 输出转换为稳定、可验证的结构化数据；
5. 依据可调阈值，把错误分为详细讲解和一句话简评；
6. 由 LLM 教练主动发起会话，给出逐错分析和整盘总结；
7. 允许用户在牌局任意时点继续追问；
8. 像 Agent 会话一样保存和恢复历史牌谱及对话。

产品的核心不是重新实现麻将 AI，而是把 Mortal 的决策证据、可操作的牌局回放和有上下文的 LLM 教学组织成一个可靠的本地 Agent。

## 2. 首版范围

### 2.1 支持

- 雀魂分享牌谱 URL；
- 常规四人麻将南风局；
- URL 指定的主视角；
- 弃牌、吃、碰、杠、立直、默听、和牌等主视角可选决策；
- 本机 Mortal 分析；
- OpenAI 兼容 LLM 接口；
- 一牌谱一会话；
- 本机会话历史、重命名、删除和恢复；
- 牌局回放、错误跳转、逐切跳转和完整事件步进；
- 每条聊天消息绑定发送瞬间的牌局局面。

### 2.2 不支持

- 三人麻将；
- 东风局；
- 特殊规则牌局；
- 天凤、雀姬、雀城等其他平台；
- 公网部署、多用户、云同步和移动端原生应用；
- 自动使用公开 Mortal 网站；
- 雀魂登录、Cookie、账号授权或任何凭据备用流程；
- 用 LLM 替代、覆盖或伪造 Mortal 原始判断。

不支持的牌谱应在分析前被拒绝，并给出具体原因，不生成可能误导的部分报告。

## 3. 关键外部约束

- `https://mjai.ekyu.moe` 的公开提交流程受 Cloudflare Turnstile 保护，不能作为后台自动化接口。
- 首版使用本地 Mortal 和本地牌谱处理流程，不自动操作公开网站。
- 雀魂牌谱获取严格为匿名流程。实现不得引入登录、Cookie 或账户状态。
- Mortal 偏好值不是胜率、打点损失或期望值。产品始终使用“Mortal 偏好”和“Mortal 偏好差”表述。
- Mortal 模型、配置和大体积权重是外部本地依赖，不提交到本仓库。

## 4. 用户流程

### 4.1 首次设置

用户设置：

- OpenAI 兼容 Base URL；
- API Key；
- 模型名；
- Mortal 可执行文件、配置和模型文件路径。

应用分别执行 LLM 连接测试和 Mortal 运行测试。两项均通过后进入工作台。

API Key 保存到 Windows 凭据管理器。前端只接收“已配置”状态，不得读取完整密钥。Base URL、模型名、阈值等非敏感设置保存在本机应用配置中。

### 4.2 新建分析

1. 用户点击“新分析”；
2. 粘贴雀魂 URL；
3. 应用解析回放标识和主视角；
4. 应用校验四麻、南风局和常规规则；
5. 创建一个新会话；
6. 后台依次执行牌谱获取、格式转换、Mortal、结构化和教练生成；
7. 前端实时显示阶段和进度；
8. 教练生成完成后主动发送开场报告。

### 4.3 继续追问

用户在中央牌桌导航到任意局面并发送消息。发送时应用冻结当前牌局快照，并作为隐藏上下文附加到该条消息。用户随后导航到其他位置，不会改变历史消息绑定的局面。

### 4.4 历史会话

每份牌谱分析是独立会话。历史列表显示自动生成的牌局名称、日期、最终名次、重点错误数和状态。用户可重新打开、继续追问、重命名或删除会话。

## 5. 界面设计

### 5.1 总体布局

桌面宽屏采用三栏结构：

- 左栏：会话历史和“新分析”；
- 中栏：视觉中心，展示牌桌、回放和决策热力；
- 右栏：教练开场报告、当前错误讲解和后续对话。

窄屏下，会话栏和对话栏变为可打开的抽屉，牌局区域保持主视图。

### 5.2 中央牌局区

中央牌局区展示：

- 四家牌河；
- 四家鸣牌和立直状态；
- 我方手牌与当前摸牌；
- 宝牌指示牌；
- 场风、自风、局数、本场、立直棒、剩余牌数；
- 四家点数和当前顺位；
- 当前事件与主视角可选动作。

在主视角可操作时，每个候选动作直接显示 Mortal 偏好分和热力。Mortal 首选与实战动作必须有不同且不只依赖颜色的标记。

### 5.3 控制器语义

- 上一局 / 下一局：移动到相邻局的开始位置；
- 上一错误 / 下一错误：移动到相邻的主视角非首选决策；
- 上一切牌 / 下一切牌：移动到相邻的主视角弃牌决策；
- 后退 / 前进：沿完整牌局事件流移动一个原子事件，包括摸牌、弃牌、鸣牌、立直和结算。

导航不会自动发送消息，也不会改变历史消息已绑定的快照。

### 5.4 右侧教练区

右侧显示：

- 教练主动开场报告；
- 当前错误的详细或简略讲解；
- Mortal 原始候选证据；
- 用户追问与教练回复；
- 消息输入框；
- 当前消息将附加哪个牌局位置的轻量提示。

## 6. 系统架构

首版采用本地 Web Agent：

- React + TypeScript 前端；
- Node.js + TypeScript 本机服务；
- SQLite 本地数据库；
- Mortal 独立子进程；
- OpenAI 兼容 LLM 客户端；
- SSE 进度和消息流。

建议代码边界：

- `coach/web`：工作台、牌局回放、热力牌面和聊天；
- `coach/server`：本机 API、任务编排、安全存储和进程管理；
- `coach/contracts`：跨前端、服务端、数据库和 LLM 的共享运行时数据契约。

现有静态教学站点继续独立工作。教练项目可复用现有 `assets/tiles` 素材，但不得破坏原页面和测试。

## 7. 数据流

```text
雀魂 URL
  → URL 解析与主视角识别
  → 匿名牌谱获取
  → 统一牌谱格式转换
  → 本机 Mortal
  → Mortal 输出解析与结构化
  → 偏好差计算与阈值分流
  → LLM 教练生成
  → SQLite 会话与消息
  → 牌局工作台
```

各阶段通过稳定的数据契约连接。牌谱获取、Mortal、结构化和 LLM 均为可单独测试和替换的模块。

## 8. 结构化分析模型

### 8.1 会话

会话至少记录：

- 会话 ID；
- 原始 URL；
- 回放 ID；
- 主视角标识和座位；
- 牌局元数据；
- 任务状态和失败阶段；
- Mortal 版本、网络标识、配置摘要和 temperature；
- LLM Base URL 标识和模型名，不含 API Key；
- 创建、更新和完成时间；
- 自动标题与用户标题。

### 8.2 牌局事件

事件流按确定顺序记录整盘动作。每个事件具有稳定事件 ID、局 ID、事件序号、操作者、动作类型和动作数据。

### 8.3 决策

每个主视角决策至少记录：

- 决策 ID、局和事件位置；
- 发送给 Mortal 的完整可见状态；
- 手牌、摸牌、牌河、鸣牌、宝牌、点数、巡目和剩余牌数；
- 合法候选动作；
- 实战动作；
- Mortal 候选排序和原始偏好；
- Mortal 首选；
- 偏好差；
- 是否为错误；
- 是否超过详解阈值；
- 讲解状态和结构化讲解。

动作标识必须能区分赤牌、普通五、立直弃牌、普通弃牌及不同鸣牌组合，不能只按牌面文本合并。

### 8.4 消息与牌局快照

每条用户消息持久化：

- 消息文本；
- 发送时间；
- 当时会话 ID；
- 局 ID；
- 事件 ID；
- 可选决策 ID；
- 完整 `scene_snapshot`；
- 对应教练回复。

`scene_snapshot` 是不可变快照，不是指向“当前播放器状态”的动态引用。

## 9. Mortal 偏好差和阈值

在固定并记录的 temperature 下：

```text
偏好差 = Mortal 首选偏好分 - 实战动作偏好分
```

界面统一显示为 0–100 的 Mortal 偏好分和偏好差。该值不描述胜率、打点或 EV。

- 默认详解阈值：10；
- 用户可在设置中调整；
- 实战动作是 Mortal 首选时，不计为错误；
- 所有非首选决策均保留；
- 高于或等于阈值的错误生成完整讲解；
- 低于阈值的错误生成一句具体简评。

一次会话必须冻结分析时使用的阈值。用户改变全局阈值只影响新会话；重新分级旧会话必须是显式操作，避免历史报告悄然变化。

## 10. 教练输出契约

### 10.1 教练开场

分析完成后，教练主动发送开场报告，包含：

1. 整盘表现；
2. 最重要的改进主题；
3. 高阈值错误数和低阈值偏差数；
4. 按重要性排序的错误目录；
5. 每局简评；
6. 整盘总结和下一步训练建议。

每个高阈值错误的详细讲解预先生成并绑定到决策。用户通过错误导航查看，不要求把所有长文堆叠在一条聊天消息中。

### 10.2 高阈值错误

完整讲解必须包含：

- 实战动作；
- 推荐动作；
- 关键候选比较；
- 错误的具体原因；
- 引用的局面证据；
- 牌效、打点、速度、防守或顺位层面的影响；
- 可迁移到其他牌局的判断原则；
- 对解释置信度的诚实说明。

### 10.3 低阈值错误

一句话简评也必须包含：

- 推荐动作或候选比较；
- 至少一个具体原因；
- 至少一个对应的可见证据。

允许的证据包括现物数量、牌形连接、有效进张、巡目、点差、宝牌、安全度、鸣牌和牌河信息。

禁止只有以下内容的空泛简评：

- “实战选择可以理解”；
- “两者差距不大”；
- “Mortal 更喜欢某牌”；
- “这是一个小错误”；
- 任何没有引用局面事实的泛泛判断。

若结构化证据不足以可靠解释微弱偏好，必须明确写出“当前结构化证据不足以可靠解释这项微弱偏好”，不得编造因果理由。

### 10.4 事实与解释

Mortal 的动作和偏好属于结构化事实。LLM 的麻将理由属于解释。界面和数据结构必须保留两者边界，避免用户把 LLM 推测误认为 Mortal 原始输出。

## 11. 隐藏提示词协议

每次 LLM 请求由四层组成：

1. 固定教练角色、术语、证据要求和禁止事项；
2. 当前会话的整盘摘要和错误索引；
3. 当前用户消息冻结的完整牌局快照；
4. 当前会话中必要的对话历史。

普通追问不重复发送整份原始牌谱，但必须始终发送用户发送消息时看到的完整有效局面。教练开场生成可以访问整盘结构化分析。

LLM 输出使用运行时模式校验。高阈值讲解和低阈值简评都必须提供可解析的证据引用。缺少必填字段、出现空泛话术或引用不存在的牌局事实时，该项输出视为无效并单独重试。

## 12. 会话任务状态与恢复

会话状态机：

```text
created
→ fetching_replay
→ converting_replay
→ running_mortal
→ normalizing
→ generating_coach
→ ready
```

任意阶段可进入 `failed`，同时记录：

- 失败阶段；
- 用户可读错误；
- 内部诊断码；
- 可安全记录的日志摘要；
- 可重试起点。

恢复规则：

- 从失败阶段重试；
- 已成功的中间产物不重复生成；
- Mortal 成功而 LLM 失败时，牌桌和结构化结果仍可查看；
- 单个错误讲解失败时，只重试该错误；
- 应用重启后恢复未完成会话；
- 不静默切换到公开 Mortal、其他 Mortal 网络或其他 LLM。

## 13. 本地存储与安全

- API Key 只保存在 Windows 凭据管理器；
- SQLite 不保存 API Key；
- 前端不接收 API Key；
- 日志必须过滤密钥、授权头、完整请求体和敏感路径；
- 雀魂侧不保存任何凭据；
- 数据库、日志和会话文件保存在用户本地应用数据目录；
- Mortal 模型文件位于用户指定的外部目录；
- 删除会话时删除该会话的牌谱、中间结果、讲解和消息。

- 高低阈值分流；
- 不同导航按钮的精确语义；

### 14.2 契约测试

- Mortal JSON 到统一结构；
- 数据库记录到前端视图；
- LLM 输入包含当前冻结快照；

### 14.4 端到端测试

## 15. 验收标准

首版完成必须同时满足：

1. 用户完成一次性 LLM 和 Mortal 设置后，每盘只输入一个雀魂 URL；
2. 不需要雀魂登录或 Cookie；
3. 非四麻南风局被清楚拒绝；
4. 能展示完整牌局、主视角手牌、四家牌河、宝牌和点数；
5. 控制器按本规格精确导航；
6. Mortal 偏好直接显示在候选牌或动作上；
7. 默认阈值为 10；
8. 所有非首选决策都有讲解；
9. 高阈值错误有完整分析；
10. 低阈值错误有具体原因和证据，不输出片汤话；
11. 教练主动发送整盘开场报告；
12. 每条用户消息都绑定发送瞬间的不可变牌局快照；
13. 分析失败可从正确阶段恢复；
14. 历史会话可保存、恢复、重命名和删除；
15. API Key 不进入前端、SQLite、仓库或日志；
16. 现有教学网站及其测试不受破坏。

## 16. 实施风险与控制

### 匿名牌谱获取发生协议变化

牌谱获取器保持独立边界并使用固定夹具测试。若匿名接口不可用，应用应明确报错；首版不以登录流程绕过。

### Mortal 输出或版本变化

记录 Mortal 版本、网络、配置和 temperature；解析层使用版本化契约和夹具测试。

### LLM 编造原因

要求结构化证据引用，校验引用存在性，拒绝空泛话术；证据不足时允许明确表示无法可靠解释。

### 长牌谱导致提示词过大

开场生成使用整盘结构化摘要和分批错误讲解；普通追问只发送整盘摘要、错误索引、必要历史和当前冻结快照。

### 本机任务资源竞争

Mortal 任务通过本地队列限制并发。前端显示排队和运行状态，应用退出或重启后恢复任务。
